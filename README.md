# 技术文档问答与故障排查助手

建立日期：2026-10-30。状态：项目方案与检索起步材料已准备，尚无完整RAG／Agent／API产品。起步材料由助手编写，核心功能由用户分步实现并验证。

## 求职目标

面向AI应用开发、RAG／Agent工程及相关技术实习。项目按岗位共通能力选择，不依赖用户硕士专业主题。

## 要实现的用户需求

输入Python或HTTP工具使用问题、报错描述，检索指定技术资料，输出有来源的解释和排查步骤。资料不足时明确缺少依据；后续通过工具查询文档版本或检查日志等结构化信息，再给建议。

示例：“接口返回404，为什么程序仍正常退出？”“timeout=10是不是请求总耗时不会超过10秒？”

## 项目主线

1. **检索基线**：读取文档记录、搜索相关片段，返回文档ID与来源；暂不生成答案。
2. **RAG最小版本**：切分与向量检索、接入一个模型API、组合上下文、返回带出处答案；API费用接入前另行确认。
3. **接口与可靠性**：FastAPI请求校验、结构化返回、日志、超时与失败处理；引入一个有明确用途的工具，而非只添加Agent名称。
4. **可衡量的改进**：固定20–30个检索／问答／失败案例，对比基线与改进，记录检索命中、依据是否支持、格式、延迟和实际成本。

RAG指先检索资料，再让模型依据检索结果生成回答。当前第一步只有关键词检索，是基线，不是完整语义检索或RAG实现。工具调用与Agent能力必须实际实现、验证后再用于项目陈述。

## 局限

1. **示例代码没有进知识库**：FastAPI的中文文档中，凡是要展示代码的地方用的都是docs_src 里对应 .py 文件的内容而不是代码本身。比如题 1 问的是怎么查看 root_path，真正的答案是 request.scope.get("root_path")，可它在代码文件里，模型拿不到，所以只答出了「响应里有这个字段」。。改进：ingest时把中文占位全部换成对应的.py文件。然后重新切块。重新向量化。重新跑开发集。
